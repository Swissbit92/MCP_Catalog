### Embodiment track ([ADR-013](decisions/013-embodied-companion-voice-before-face-live2d-primary-3d-desktop-as-a-separate-track.md))

An embodied face is a **product requirement**, not an enhancement — but it is sequenced strictly behind voice, because lip-sync and expression timing are audio-derived. Steps 1–3 are worth doing on their own merits even if no avatar ever ships, so the track cannot strand on the face.

- [ ] **1. Local TTS on the Mac Mini** — greenfield; nothing in the stack synthesizes speech today (verified 2026-08-02: zero hits for `tts|piper|kokoro|elevenlabs|coqui|xtts` outside a superseded `archive/phase7/` planning line). Front-runner: **Kokoro-82M (Apache-2.0) via `mlx-audio`** — MLX-native for Apple Silicon, ships an OpenAI-compatible REST API so it drops into FastAPI. **Licence traps to avoid:** XTTS-v2 is permanently non-commercial (Coqui dissolved, nobody left to sell a licence); Piper's maintained fork (`OHF-Voice/piper1-gpl`) is GPL-3.0, not the MIT most tutorials still cite.
- [ ] **2. Sentence-chunked response streaming** — the coordinator is fully blocking today (no SSE/WebSocket anywhere; `POST /sessions/{id}/chat` returns the whole completion). Buffer Ollama's token stream, split on sentence boundaries, and fire TTS on the first completed sentence rather than waiting for the full generation — the difference between sub-second first audio and a multi-second silence. Supersedes the gateway-only streaming item above: build it once at the coordinator and both thin clients inherit it.
- [ ] **3. Phone access — Tailscale + PWA** — **hard prerequisite, currently blocking.** `scripts/serve_frontend.py:99` binds `HTTPServer(("127.0.0.1", PORT))`, so the React UI is not reachable from a phone at all; NEPHILIM's only mobile channel today is the Telegram gateway, which by protocol can never render an avatar. Mobile-primary + a required face means the React app has to become the primary phone surface. Also decide Telegram's role: lightweight text channel alongside the PWA, or retired.
  - Related: **iOS Safari requires a user gesture before audio plays**, so proactive speech needs a deliberate "tap to wake her" interaction. Design it in during step 1, not after.
- [ ] **4. The face — Live2D, one persona, behind a flag.** Live2D rigs the persona art already owned (~73 MB across 6 personas), so each stays recognisably herself; VRM would mean recreating all six in 3D and they would not match. Also ~3 MB vs ~30 MB per character, far lighter on a phone GPU, matches the existing gacha idiom, and carries no third-party licence flags. **A per-device split (3D desktop / 2D mobile) is explicitly rejected** — it doubles the art cost, doubles every downstream feature, and fractures the companion's identity across devices. One rig everywhere; desktop gets higher fidelity, not a different character.
  - Expression signal — pick one: the existing keyword-heuristic `EmotionalState` (`current_mood`/`mood_intensity`, already live per-turn at `GET /sessions/{id}/emotional-state`), LLM-emitted bracket tags (cheapest, and improves text chat independently of any avatar), or implementing the PAD triplet designed in [ADR-006](decisions/006-companion-memory-and-continuity-eval-first.md) Phase 2 and still unbuilt.
  - Battery obliges a render policy — animate during speech, idle low-FPS or static otherwise. `LegendaryParticles.tsx:178` already sets the precedent by disabling particles below 768px.
  - Drive the mouth from a WebAudio `AnalyserNode` on the TTS node — **never** an OS audio tap. Taps are per-process not per-stream (a browser tap would lip-sync to any other tab's audio) and do not exist on iOS/Android at all.
